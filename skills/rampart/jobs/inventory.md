# Job: inventory — map a folder's systems into a confirmed project

Builds or updates one project's `project.json`: its systems, where they live, how critical they are, and the owner attestation every audit needs. Nothing is audited.

## Arguments

- `[folder]`: the folder to map; default the working directory. Resolve it to an absolute path.
- `--slug <slug>` and `--name <name>`: passed to the scanner. A slug is 2 to 40 characters of `a-z`, `0-9` and `-`; to add a folder to an existing project, the user passes that project's slug.

## Steps

The job reports its steps as it goes, by the Job progress rules of [dashboard](${CLAUDE_SKILL_DIR}/jobs/dashboard.md): "report `<command>`" means run that `progress.cjs` command, then write what it printed to the live dashboard when the job is live. The page shows a project only once it is in the dashboard's database, so for a project the store does not hold yet (step 2 does not list it) the commands run but only the last one, the finish after the sync, is written.

1. **Scan.** Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/inventory-scan.cjs" "<folder>" --json`, adding `--slug` and `--name` when given. It prints `{systems, draft}`; every system in it is marked `source: "inferred"`. If it exits 2 asking for `--slug`, ask the user for a slug and run it again with one; any other exit 2: relay its line and stop. If `systems` is empty, say nothing recognizable was found in that folder and stop.
2. **Existing project.** Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/store.cjs" projects`. If the draft's slug is listed, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/store.cjs" project <slug> --json` and keep it for the steps below. Its attestation is never carried over: the user gives it again in step 5.

   Then run `node "${CLAUDE_PLUGIN_ROOT}/scripts/store.cjs" dashboard --json` and keep its `url`, and report `node "${CLAUDE_PLUGIN_ROOT}/scripts/progress.cjs" start --project <slug> --job inventory` (adding `--live` when there is a `url`), `node "${CLAUDE_PLUGIN_ROOT}/scripts/progress.cjs" step --project <slug> --step scan --status done --note "<N> parts found"` and `node "${CLAUDE_PLUGIN_ROOT}/scripts/progress.cjs" step --project <slug> --step map --status running`, as one write.
3. **Map.** This is the one cost question. Unless the user's request already asked for the mapping agent, ask with AskUserQuestion: `header: "Mapping"`, `question: "Refine the draft with one small agent run (names, live URLs and hosts it can see in the folder's docs and config)?"`, options "Yes (Recommended)" and "No, use the scanner's draft". On "Yes", dispatch `rampart:inventory-mapper` with the folder's absolute path, the scanner's JSON verbatim, and the stored project JSON from step 2 if there is one. It answers with a draft JSON and a list of open questions. Use its draft, but restore from the scanner's draft any `id`, `type`, `packs`, `layers` or `repo` it changed, drop any `live` or `host` value it gives without naming the file it came from, and ignore anything it says about the attestation. On "No" or no answer, carry on with the scanner's draft. Report the `map` step `--status done`, or `--status skipped --note "the scanner's draft was used"` when no agent ran.
4. **Merge and show.** With a stored project, match each scanned system to a stored one: by `repo.remote` and `type` when both sides have a remote, else by `id` and `type`. A match keeps the stored `id`; its stored `name`, `criticality`, `live`, `host` and `executor` win over the draft's guesses; and its `repo.paths` becomes the stored entries plus this machine's from the draft. A scanned system with no match whose id is taken gets the id `<id>-2`. Stored systems the scan did not match are added to the draft. The output's top-level `machineId` is not part of the project: never copy it into the draft. Then show one line per system: id, type, name, live URL, SSH target, each guessed value marked "(guess)"; then the mapper's open questions as a short list, leaving out any that seems to hold a credential value. Never show `evidence` or `repo.paths`.
5. **Ask.** Report `node "${CLAUDE_PLUGIN_ROOT}/scripts/progress.cjs" step --project <slug> --step questions --status running` before the first question, and the same step `--status done` after the last. Use AskUserQuestion, at most four questions per call and as few calls as fit. Put the current value or guess first, marked " (Recommended)". An answer typed in the tool's free-text entry is taken as the value. In this order:
   - `header: "Criticality"`: the project's criticality; options `high`, `medium`, `low`.
   - `header: "Executor"`: options "Local only" (sets `defaultExecutor: "local"` and `cloudAllowed: false`; the default) and "Local, cloud allowed for repo jobs" (sets `cloudAllowed: true` and leaves `defaultExecutor: "local"`; cloud runs arrive in a later version, so until then its jobs run locally too).
   - One per system, `header` its id cut to 12 characters: "What does <name> guard?"; exactly four options, `auth`, "billing or data", `public` and `internal`, with the option that holds the guess first (with no stored value and no mapper guess, `public` goes first without " (Recommended)": it is how a system without one is weighted, not a guess). It sets the system's `criticality`, which weights the project score: "billing or data" sets `billing` when the guess was `billing`, else `data`, and the user can type the other.
   - One per web system (`web-nextjs`, `node-api`, `cloudflare-workers`, `wordpress-hostinger`, `static-site`), `header: "Live URL"`: "Live URL for <name>? Type it, or pick:"; options its current URL when there is one (stored, or found by the mapper, naming the file), then "Not deployed" and "Skip for now". It sets `live.url`, which must start with `http://` or `https://`; the other two leave it out.
   - One per host system (`supabase`, `n8n`, `docker-host`; the scanner leaves them without a `host`), `header: "SSH host"`: "How is <name> reached? Type `user@host, compose project, config path` (the last two optional), or pick:"; options its current value when there is one (stored, or found by the mapper, naming the file), then "Not over SSH from here" and "Skip for now". It sets `host.ssh`, `host.composeProject` and `host.configPath`; with no SSH target, leave `host` out.
   - Last, alone in its own call: `header: "Attestation"`, `question: "Do you own, or are you authorized to test, every system listed here?"`, options "Yes" and "No", neither marked recommended. Never answer it or assume it.

   A typed value that should be a URL or `user@host` and is not gets asked once more; after that, leave it out and say so. The same goes for a URL with a user, password or token before the host (`https://user:pass@…`) and an SSH target with a password (`user:pass@host`): the store refuses them, so never write one into the draft, never repeat it back, and ask once for the address without it.
6. **"No" to the attestation, or no answer:** save nothing. Report `node "${CLAUDE_PLUGIN_ROOT}/scripts/progress.cjs" finish --project <slug> --status failed --note "nothing saved: the owner attestation was not given"`. Say that audits need the attestation and that `/rampart inventory` can be run again. The job ends here, with no score or render.
7. **Build the project.** Apply every answer to the draft. Run `git config user.name` and `date -u +%Y-%m-%dT%H:%M:%SZ`, then set `ownerAttestation` to `{"statement": "I own or am authorized to test every system listed here", "by": "<the name, or unknown when git printed nothing>", "at": "<the date>"}`. Set every system's `source` to `"confirmed"`. Keep the ids, `packs`, `layers`, `repo` and `evidence` as drafted.
8. **Write and save.** Report `node "${CLAUDE_PLUGIN_ROOT}/scripts/progress.cjs" step --project <slug> --step save --status running` when step 7 begins and `--status done` once `project-save` exits 0 (`failed`, with its reason in a few plain words, when it stops the job; then finish as step 10 says, with `--status failed`). Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/doctor.cjs" --json` and read `store.home`; if it is null, relay its degraded line and stop. Write the project JSON with the Write tool to `<store.home>/drafts/<slug>.project.json`, then run `node "${CLAUDE_PLUGIN_ROOT}/scripts/store.cjs" project-save "<that file>"`. Exit 0 prints the slug. Exit 1 lists the invalid paths: correct those fields (ask the user only for a value only they know), write the file and save again, at most twice. Never touch `ownerAttestation` to make it pass. Exit 2: relay its line and stop.
9. **Finish** as the shared rules say: report `node "${CLAUDE_PLUGIN_ROOT}/scripts/progress.cjs" step --project <slug> --step score --status running`, score, then render, then report the `score` step `--status done`. Summarise the slug, its systems, and what is still missing and what that skips (no live URL: no headers check; no SSH target: no INFRA audit). Suggest `/rampart audit L1` next.
10. **Live dashboard.** When `node "${CLAUDE_PLUGIN_ROOT}/scripts/store.cjs" dashboard --json` shows a `url`, report `node "${CLAUDE_PLUGIN_ROOT}/scripts/progress.cjs" step --project <slug> --step sync --status running`, follow the Sync section of [dashboard](${CLAUDE_SKILL_DIR}/jobs/dashboard.md) for this project, and add its one line to the summary; a failed sync is a note, not a failed inventory. Then run `node "${CLAUDE_PLUGIN_ROOT}/scripts/progress.cjs" step --project <slug> --step sync --status done` (or `failed` with the reason in a few plain words); its document is written with the finish. Last, with or without a `url`, report `node "${CLAUDE_PLUGIN_ROOT}/scripts/progress.cjs" finish --project <slug>`.
