# Changelog

## Unreleased

- **The dashboard counts calendar days, not 24-hour spans.** "Last checked 2026-11-12 (today)" appeared on the 13th, because a check from the previous evening was under 24 hours old and `since()` floored the elapsed time. It now compares the viewer's local calendar dates, so that check reads "yesterday". The date itself was always right (it is the viewer's local date).

- **The `sshd-effective` probe can finally run, without Rampart gaining privilege.** `sshd -T` needs root, and the audit connects as an ordinary user, so the probe failed on every host and a drop-in file that overrides the main SSH config could go unseen. The probe now reads `/var/lib/rampart/sshd-effective.txt`, a file the host's owner has a root job write: `# exported <UTC time>` and the effective authentication settings, never keys. No file means the probe is unavailable, as before. Setup on the host, once: create `/usr/local/sbin/rampart-sshd-export` (root, mode 755) containing `#!/bin/sh`, `set -eu`, `mkdir -p /var/lib/rampart`, then `{ echo "# exported $(date -u +%Y-%m-%dT%H:%M:%SZ)"; /usr/sbin/sshd -T | grep -i -E '^(passwordauthentication|kbdinteractiveauthentication|challengeresponseauthentication|permitrootlogin|permitemptypasswords|authenticationmethods|pubkeyauthentication|port) '; } > /var/lib/rampart/sshd-effective.txt.tmp`, `chmod 644 /var/lib/rampart/sshd-effective.txt.tmp` and `mv /var/lib/rampart/sshd-effective.txt.tmp /var/lib/rampart/sshd-effective.txt`; then `/etc/cron.d/rampart-sshd` (root, mode 644) with `*/30 * * * * root /usr/local/sbin/rampart-sshd-export`. The test that forbids `sudo` in a probe stays: Rampart still runs nothing with privilege. docker-host pack 1.1.0.

- **Supabase INFRA probes work on Docker Compose's default container names.** `auth-env`, `service-env` and `default-secrets` hard-coded the official `supabase-*` names, so a stack named by Compose (`<composeProject>-auth-1`) answered `No such object` for all three. Probe argv may now carry `<container:SERVICE>` (auth, rest, storage, functions, db, kong, envoy). The runner expands it to `<host.composeProject>-<service>-1` when the system records a project name (lowercase letters, digits, `-` and `_`, up to 63 characters; anything else is ignored) and otherwise to the official name (`functions` is `supabase-edge-functions` there), so systems without `host.composeProject` behave as before. `default-secrets` now probes only the auth and db containers, which always exist, so only exit 0 is an answer and a wrong name never earns coverage. The gateway check moved to a new `default-secrets-gateway` probe that lists kong and envoy and declares `okExit: 0,1`, because Docker exits 1 for the one gateway a stack does not run. Supabase pack 1.1.0, `lastReviewed` 2026-11-13.

## 0.5.0-alpha.1 — 2026-11-12

On a large Expo app (about 1,100 files) the 0.4 dry run planned 565 hunters at low effort and 1,356 at medium (56.5M and 135.6M tokens by its flat estimate); a test medium run dispatched close to 1,000 hunters and produced one candidate. Most of that spend went to hunters reading screenshots, Markdown and cache folders, or tiny folders one class at a time. The coverage ledger, L2 diff scoping, the score and the dashboard still key on the same directory units; only the dispatch changed. The same app now plans 33 hunters at low and 66 at medium, about 2.8M and 5.8M tokens of context by the new estimate.

- **A hunt reads everything but known non-code.** The filter is a denylist. A file is read unless it is an image, font, media file, archive, binary, office document, prose (Markdown, plain text, licence files), data (csv, logs, source maps, snapshots), a stylesheet, a lockfile, minified or generated output (`*.min.*`, `*.bundle.js`, content-hashed chunks), a translation table (a data or string file under `locales`, `translations`, `i18n` or `l10n` with a locale code in its path), or in an editor or cache folder (`.vscode`, `.idea`, `.expo`, `.cache`, `__mocks__`, `__snapshots__`). Unknown and extensionless files (`bin/www`, `Rakefile`, `Fastfile`, templates and views in any language) are read. In a git checkout the file list comes from git, tracked files (submodules included) plus untracked ones git does not ignore, so ignored build output drops out; outside git the old walk is used. A submodule that is not checked out is listed as not hunted. `DEFAULT_IGNORE` and the reachable/background split are unchanged.
- **What is not read stays visible.** Source over 200 KB, and JSON over 64 KB, is not given to a hunter, but `units.json` and `REPORT.md` list each such file with its size, and a folder whose code is all over the cap is a unit with status `not-hunted`: planned, not covered, and a gap in the ledger. Every other excluded file is counted by class in `units.json` (`excluded.byClass`) and the report. A directory with no file a hunt reads at all is no unit: it is never planned, never a gap, and never counted against coverage. An L2 branch whose changes are all excluded files is `empty`, and its message says what was left out ("the 2 changed files are not source a hunt reads (1 image, 1 prose)").
- **Credential files are named, never read.** `.env` and `.env.*` (except templates), `.dev.vars`, `.npmrc`, keys, keystores and `credentials*`/`service-account*` files never reach a hunter's `files`. They are passed as a separate `present` list that the dispatch and `agents/hunter.md` both say never to open; a candidate may point at one.
- **Hunt groups and class bundles.** The units are packed, in sorted order so siblings stay together, into hunt groups of about 120 KB of source (`GROUP_BUDGET_BYTES`). A unit over that is split by files into groups of its own, and reachable and background units never share a group. The effort's classes are cut into bundles of up to six (`BUNDLE_SIZE`), as even as possible and never mixing two packs: low's five logic-bug classes are one bundle, twelve classes are two. One `hunter` hunts one bundle over one group, so hunters = groups × bundles, keyed `<group>__<bundle>` (`g03__b1`). Each candidate names its own class, which must be one of the hunter's bundle, and a file of the group; its unit is that file's unit. A hunter that does not return fails every unit of its group. `units.json` records the `groups` (with their files) and `bundles`. The report notes that a group can span unrelated folders and that each hunter hunts several classes in one pass.
- **Incremental L3, and when it does not skip.** An L3 audit skips a unit (status `unchanged`, its ledger entry kept, counted as covered in the run's credit, closing nothing) only when all of these hold:
  - its ledger entry is `complete`: no hunter of it hit the cap, it had no invalid entry, and every candidate in it was decided with at least two votes;
  - the entry was written by this hunt engine (`engine`, `HUNT_ENGINE` in `scripts/hunt-plan.cjs`, bumped whenever the source filter, grouping, bundle size, hunter prompt or hunter model changes; 0.4 entries never qualify), at the same pack versions and with every class the effort hunts;
  - the hunt finished within the system's L3 cadence (`cadenceDays`, default 90 days), so even an untouched unit is hunted again once per cadence;
  - the covering run's revision was clean and its commit is still in the checkout;
  - none of the unit's files changed since that commit, and no cross-cutting file changed anywhere in the repository (`CROSS_CUTTING`: middleware, routing and app entry files, auth, session and policy code, config, migrations and SQL, Prisma and other schemas, CI and infrastructure files, manifests and lockfiles, and any root-level file). A hunter reports a flaw only where its sink is, so a removed middleware or RLS policy elsewhere would otherwise go unseen. Files marked assume-unchanged or skip-worktree count as changed.

  When nothing needs hunting, init says so and creates no run. `--full` hunts every unit again. A unit whose source changed also drops the classes earlier runs hunted on its old code. The report lists the skipped units and says that a skip cannot see every flaw a change elsewhere opens.
- **An empty plan says why.** The dry run gives each effort with no hunter a `reason` and `message` (no source a hunt reads, none reachable at this effort, every source file over the size cap, or every unit unchanged), and init returns the same instead of exiting with an error.
- **No closing on a relabel.** A bundle hunter may report a flaw under a different class of its bundle, which gives it a new id. A finding is no longer closed when this run has any candidate at the same path (and symbol, when both have one), of any class and whatever its verdict.
- **Up to 20 candidates per hunter.** A bundle hunter covers more code and more classes than a one-class hunter, so refs now run `c1` to `c20` (hunt-io, the candidate schema and the workflow agree). A hunter at 20 still closes nothing in its units. The INFRA prober keeps its cap of 10.
- **Models.** `hunter` runs on Sonnet: there are many of them and they read a lot of code. `verifier` runs on Opus, because verifiers are the precision gate that decides what becomes a finding. The infra prober still inherits the session's model.
- **An estimate worked out from the plan.** The flat 2 × hunters × 50,000 tokens is gone. A hunter's estimate is its group's source at 4 bytes per token, plus about 26k tokens of overhead and tracing and 4k per class with the class text. Verifiers follow an expected 0.1 candidates per hunter (one measured medium run gave 1 candidate from close to 1,000 hunters) at 2.2 votes each, about 50k tokens per vote. The constants are documented in `scripts/hunt-plan.cjs` (`ESTIMATE`). It is a rough context-size estimate (`tokensNote` in the dry run): real multi-turn runs resend context and can use several times more. The dry run keeps `units`, `classes`, `hunters`, `workflows`, `agents` and `tokens` per effort and adds `groups`, `bundles`, `skippedUnchanged`, `notHunted`, `sourceBytes`, `verifiers`, `hunterTokens` and `verifierTokens`, plus `excluded` for the whole repository.
- **The workflow** takes `groups` and `bundles` instead of `units` and dispatches one hunter per pair with the group's files, its `present` files and each class text of the bundle. A bundle with a class whose text is missing dispatches no hunter, so its units fail instead of being credited with a class no one hunted. It verifies only candidates whose class is in the bundle, and each verifier gets the text of its candidate's class. Almost every audit now fits one workflow batch.
- `revision.dirty` now looks only at the checkout's own folder when the repository is a folder of a larger one. Run directories written by 0.4 (one-class hunters keyed `<unit>__<classId>`) still assemble as before.

### Rulings superseded

These earlier design rulings of the hunt engine are replaced:

- R3 and R4: hunters are planned per group and bundle, not per unit and class; the hunter key is `<group>__<bundle>`. Older keys are still read.
- R6: the hunter replies `{group, classIds, candidates: [{ref, classId, title, severity}]}`.
- R2 and R49: refs `c1` to `c20` and a cap of 20 for a group hunter; 10 stays for the INFRA prober and for 0.4 run directories.
- R32: L2 and L3 workflow args carry `groups` with their files in place of `units` with `paths`, and L3 `units.json` now records the files, on its groups.
- R46 is extended: a finding also stays open when this run has any candidate at its path (and symbol), whatever the class or verdict, and a group hunter closes only in files it read.
- R33: the workflow no longer applies the low-effort class filter itself. It hunts exactly the bundles init printed, since init already applied the effort.
- The agent test that pinned "no model key" on the hunter and verifier now pins `sonnet` and `opus`.

### Known limitations

- A unit covered by a run on a dirty tree is hunted again on every later L3 run until a run on a clean tree covers it.
- Packing is greedy: a group can close well under the budget when the next unit does not fit.
- The cross-cutting list is wide on purpose. In a repository where migrations or config change often, most L3 runs hunt everything.
- A skip still looks only at files: a change outside the repository (a dashboard setting, a deployed policy) cannot make a unit changed.

### Also in this release (merged after 0.4.0-alpha.1)

- **Packs reach the live dashboard.** The sync now pushes each installed pack's public facts (name, version, last reviewed, what it applies to, class and probe counts) to the DB's `packs` collection, once per cycle through `sync-plan.cjs push --packs`, and reads that collection in its snapshot so later pushes are pinned. A dashboard synced before this version gets every pack on its next sync.
- **Packs on the page.** The dashboard lists the installed review packs in a read-only Review packs table under the project tiles (name, version, last reviewed, the system types it applies to, kinds, class and probe counts), from the DB's `packs` collection in live mode and from the static render, whose data now carries the same documents (`buildPage().packs`). Nothing of a pack's text, folder or file name reaches the page.
- **A partly covered layer reads as partial, not aging.** A layer within its cadence whose last run covered only some of its units (the partial credit above) used to show in the dashboard's freshness strip as aging, the past-its-cadence state. It now has its own state, **Partial**, with a half-filled segment, its own colour in both themes, a legend entry, the covered share in the segment's title and in the score sheet cell (`Partial · 30 d · 84% of units`). Fresh, aging, stale, never run and not declared mean what they did; a partial layer past its cadence ages and goes stale as before.
- **Large hunts run in batches.** The workflow runner starts at most 1,000 agents per workflow run, and a medium L3 audit of a 99-unit repository planned 1,188 hunters in one, so 189 never started. `hunt-io.cjs init` now prints L2 and L3 plans as `batches` of at most 400 hunters each, which leaves room for their verifiers; the audit recipe runs them one after another into the same run, and the dry run shows how many workflow runs each effort takes. The workflow itself stops starting agents at the cap (`args.agentCap`), so anything past it fails its unit instead of disappearing, and returns `agents` and `capReached`.
- **Partial runs earn partial credit.** A hunt run records the units it planned and covered (`coverage` in `run.json`), and a done run that left units failed earns only the covered share of the layer's coverage credit (83 of 99 units: 0.84), instead of full credit. The score sheet shows the share, and the audit summary names the failed units.
- **Jobs report their steps.** The audit (every layer), verify and inventory recipes now call `scripts/progress.cjs` at each step, so the dashboard's activity panel shows the job as it runs and the static page shows the last one. The rules sit once, in the dashboard recipe's new Job progress section: a write happens only when the project has a live dashboard, as one pinned `ArtifactData set` on `progress/<slug>` with the printed document, verbatim; commands with nothing slow between them share one write; a hunt reports its counts after every fourth wait and after each batch; and a progress failure is a line in the summary, never a failed job. A watch session tags the steps with the dashboard job's id. The sync neither reads nor pushes `progress` (each job writes its own, and a sync runs in the middle of a job, so a snapshot's version would be stale by the job's next write); the publish check now lists the collection. `progress.cjs` now matches the 0.5.0 run layout (refs up to `c20`, units skipped as unchanged or too large named in the hunt step's note, a verify run's double-checks) and labels steps with the page's words: AI reviewers, AI checkers, code groups.
- **The dashboard prices a hunt from the planner.** The Run-button cost sheet (`jobs.cjs costEstimate` and its copy in the page) priced an L2 or L3 job with the 0.4 rule of thumb, units × classes × 2 agents × 50,000 tokens, which overstated a 0.5 hunt many times over. The page cannot walk a repository, so the figures now come from the planner itself: each sync runs `hunt-io.cjs estimate --project <slug>`, the dry run of every L2 and L3 layer of the project's systems that have a checkout on that machine, and stores per effort the AI reviewers, agent runs, tokens and what is skipped as unchanged or not hunted (`estimates.json` in the store, `estimates` in the project document). The sheet shows those for the project's effort, with the date they were planned, the tokens labelled a rough estimate as in the audit recipe. With no stored figures it says the cost is shown when the check starts, and the job is queued with `costEstimate.agents` null (the job schema allows it); the plan step's note in the activity panel then carries the cost. INFRA is priced at its cap, at most 31 agent runs, as the dry run does. A watch session passes the project's effort to the audit, and runs an L2 or L3 job only while the fresh dry run stays within one and a half times the confirmed agent runs (or the job was confirmed with no figure); past that the job fails and asks to be started again. `jobs.cjs cost` takes `--estimate <file>` in place of `--units`, `--classes` and `--probes`.
- **A `static-site` review pack.** The scanner's type table named a `static-site` type with no pack behind it. `packs/static-site.md` (1.0.0) covers what goes wrong in a site built ahead of time and its build, in nine classes: gated content shipped to every visitor (`authz-scoping`), build-time secrets inlined into the bundle through `PUBLIC_`, `VITE_`, `GATSBY_` and similar variables or `define` (`secrets-handling`), DOM XSS from content or URL values (`dom-xss`), third-party scripts without integrity or from URLs others control (`third-party-scripts`), open redirects in client code and redirect files (`open-redirect`), forms and client calls that write with the owner's key (`client-write-endpoints`), sensitive files published from the public folder, source maps included (`published-files`), builds and CI that run or fetch untrusted input (`build-pipeline-input`), and host config files (`.htaccess`, `_headers`, `_redirects`) that weaken the site (`misconfig`). Of the five low-effort ids it keeps only `authz-scoping`: the others are server problems, so a low hunt of a static site hunts that one class. The pack test now holds the static-site pack to the fixed ids that apply to it instead of all ten. The sync pushes the pack like any other.
- **The inventory scanner finds Astro sites.** `astro` in the dependencies of the folder's `package.json`, or of an npm workspace that the root `package.json` lists (`workspaces` as exact folders or `<folder>/*`, such as `site/package.json`), is now a system. With a server adapter (`@astrojs/node`, `@astrojs/vercel`, `@astrojs/netlify`), or an `astro.config.*` that asks for `output: 'server'` or `'hybrid'`, it is a server-side app of type `node-api` with the `node-api` and `static-site` packs; with `@astrojs/cloudflare` it is `cloudflare-workers` with that pack and `static-site`; without either it is a `static-site`. The scanner opens the workspace manifests and the Astro config for this, nothing else. pnpm's `pnpm-workspace.yaml` is not read, and other frameworks are still detected only in the folder itself.
- **Run documents are keyed per project.** A run id is a time to the second, and the live database keyed a run summary by run id alone (`runs/<runId>`), so runs of two projects started in the same second overwrote each other (four run documents of one dashboard could not be pushed). The key is now `runs/<slug>--<runId>`; the body still carries `project` and the bare `runId`, and the page reads both the new and the old key, one run per run id. Within one project ids were already unique: `store.createRun` claims each id with its run directory and moves to the next second when it is taken. **Migration**: `sync-plan.cjs push` takes the cycle's snapshot (`--in "<sync>/db"`, now in the Sync recipe). On the first sync after the upgrade it pushes every local run the database lacks under its new id, whatever the push cursor says; copies an old `runs/<runId>` of the project that no local run matches (one pushed from another machine) to the new id; and deletes each old document of the project, pinned to the version the snapshot read, in batches after every write. An old document of another project, or one naming no project, is left for that project's push. A refused batch redoes the cycle as before, and the next sync finds nothing left to move.

## 0.4.0-alpha.1 — 2026-10-26

The hunt engine: Rampart's own agent audits for changes, whole repositories and self-hosted hosts.

- **Grades are no longer capped at C.** Repo systems declare L2 and L3 and hosts declare INFRA; those layers now have engines, so a finished L2, L3 or INFRA run earns its coverage credit and a clean project can reach an A.
- **`/rampart audit L3`**: a deep hunt of a whole repository. The repository is split into units, and the `rampart:audit` workflow runs one `hunter` agent per unit and pack class, at `low` (the five logic-bug classes: record scoping, tenant isolation, bulk export, sessions, search injection), `medium` (every class, reachable code) or `high` (every class, every unit) effort, with the agent count and a rough token estimate shown before anything runs.
- **`/rampart audit L2`**: the same hunt on what a branch changed against its base (`--base`, default the system's default branch); only the units holding changed files are hunted.
- **Independent verification.** Every candidate goes to fresh `verifier` agents told to disprove it. It becomes a finding only when a majority confirm it, with two confirmations for anything HIGH or CRITICAL; rejected and undecided candidates stay in the run directory, and the run's `findings.json` lists their ids. A unit whose hunter did not return is marked failed, never clean, and closes no findings.
- **A hunt closes only what it looked for.** A finding is closed as fixed only in a covered unit whose hunters hunted its class, and for L2 only in a file the hunters read; a unit whose hunter returned invalid entries or the most candidates it may (10) closes nothing, and the report says so. A run that covered fewer than half its units finishes failed, with no coverage credit.
- **Coverage remembers the classes.** The coverage ledger records the classes hunted on each unit and the effort; `coverage.cjs gaps` lists a unit until every class of its packs was hunted, and `REPORT.md` names the classes hunted and, under Skips, the ones a low effort left out.
- **`/rampart audit INFRA`**: the read-only probes of a host's packs (Docker host, Supabase, n8n, WordPress) over SSH or HTTP, with environment values scrubbed and every output redacted before it is written; one `infra-prober` agent compares the observations with the pack's baseline, and verifiers judge each candidate from the same observations. It refuses to run from a cloud session. A probe counts as covered only when it answered: exit 0 (or an exit code its pack declares healthy with `okExit`), or an HTTP status below 500; a permission error, a stopped Docker daemon or a 503 leaves its probe uncovered, and nothing is closed until every probe answered.
- **The live dashboard runs hunts too.** Its Run buttons now cover L2, L3 and INFRA, `/rampart watch` runs those audits and `verify` jobs from the queue, `verify` ends with the dashboard sync like the other jobs, and the post-push hook's `/rampart audit L2` suggestion is on.
- **`/rampart verify`**: re-judges open hunt findings against the current code with one fresh verifier each; a finding it can no longer reproduce is closed as fixed.
- **A `REPORT.md` per run**: title, headline, coverage, findings by severity, skips and the score after the run.
- **Review packs**: eight versioned packs (`packs/`) for Next.js, Node APIs, Expo, Cloudflare Workers, Supabase, n8n, Docker hosts and WordPress, each with hunt classes (look for, confirm by, disprove by, severity, CWE), a baseline and probes; `scripts/packs.cjs` lists, shows and validates them.
- **claude-security import**: `/rampart audit L2|L3 --import` records a claude-security report's findings (panel-verified, so stored as verified) without hunting, and never changes a finding's status. An attended L2 or L3 audit offers the hand-off once when the plugin is installed.
- The skill also pre-approves a plugin script run with no arguments, so a session outside auto mode no longer stops on a permission prompt at the final dashboard render.
- A grep probe whose pack declares `okExit: 0,1` (docker-host's `container-hostconfig`, where no match means no risky container flags) counts a match of nothing as a clean answer instead of a failed probe; any other grep that exits 1 is not an answer.

### Known limitations

- The `verifier` cannot run probes itself: an INFRA candidate is judged only from the observations the run already recorded.
- Some probes exit non-zero with a normal answer (`cat` of a Docker daemon configuration that does not exist, `trivy --version` where Trivy is not installed, the APT auto-upgrades file on a non-Debian host). The prober still reads them, but their probe is not covered, so on such a host an INFRA run closes no findings until the pack declares those exits with `okExit`.
- Agent write confinement is prompt-only: hunters, verifiers and the prober are told to write one file in the run directory, and nothing enforces it beyond your session's permissions.
- Hunters and verifiers read git history only when the session's working directory is the repository root; otherwise they judge the working tree alone.
- The INFRA environment scrub is line-based: a minified one-line JSON object passes to `redact()` only.
- The cost shown before a hunt is a rough estimate (a fixed token figure per agent run), not a measurement.
- One flaw can surface as several findings, one per pack class that catches it (an unscoped export found as record scoping, tenant isolation and bulk export); each is verified on its own.
- The `infra-prober`'s extra probes run only when your session allows the probe script: its agent definition lists the command but does not grant the permission, so outside auto mode or a matching allow rule it works from the recipe's probes alone.
- In a headless session (`claude -p`) nothing can be asked: the inventory saves nothing without the attestation, and an audit runs only when the request names the effort (`--effort`) and accepts the cost in words.
- Real gitleaks and trivy runs, and real SSH hosts, were not exercised on the build machine; acceptance used fixtures, a fake `ssh` and canned probe output.

## 0.3.0-alpha.1 — 2026-10-26

The live dashboard (Plan 3). Acceptance was run against a live published artifact with fixture data.

- **`/rampart dashboard` publishes a live claude.ai dashboard.** The page is a private artifact whose database is the record: projects, findings, runs, jobs, executors and meta. Only the owner can write; everyone else reads.
- **Findings carry dispositions.** The owner marks a finding fixed, false positive or accepted risk from the page, with a reason for the last two, and the decision is signed with the owner's user id.
- **Job buttons show cost and route before they queue anything.** A Run button queues a job with its estimated cost and the route that will run it (a local executor in this release). Only layers with an engine get a button (L1 for now).
- **Settings live on the page.** The owner sets them in the dashboard and the executors read them from the database.
- **Findings export as JSONL or SARIF.** SARIF 2.1.0 has one result per open finding, a stable fingerprint, no evidence text, and the plugin version as the tool version. The files are named `.jsonl.txt` and `.sarif.json` to fit the downloads allowlist.
- **`/rampart dashboard --sync` mirrors the local store into the dashboard database.** It pulls the page's decisions, settings and jobs first, then writes versioned documents; once published, the database is the record of truth and the local store a cache plus each run's raw output.
- **`/rampart watch` runs queued jobs.** It claims a job with a version-pinned write, so two executors never run one job. Use `/loop /rampart watch` to keep it running.
- **`/rampart schedule` sets up a weekly sync and the overdue L1 audits.**
- **Two hooks.** SessionStart adds a one-line note when a tool a stored project needs is missing, from a doctor report cached per day, and is silent otherwise. After a `git push` from a stored project's repo folder, the post-push hook suggests `/rampart audit L2 --project <slug>` once per session, but only once L2 is available (the hunt engine); on this release alone it stays silent.

### Known limitations

- No apply or fix yet; that is Plan 4.
- Cloud runs are off in this release: every job runs on a local `/rampart watch` executor, even on a project that allows cloud. They arrive with a cloud executor in a later version. Remote Control is optional; with it, the page nudges a watch session to run a job at once.
- Verify, L2, L3 and INFRA jobs wait for the hunt engine (Plan 2). The post-push L2 nudge and the verify sync line arrive when the branches meet.
- Acceptance used fixture data, not a real audit's findings.

## 0.1.0-alpha.2 — 2026-10-23

Fixes from the whole-branch review of alpha.1.

- **Secrets reports are stored without the matched value.** A gitleaks report written without `--redact` (gitleaks' default, and what a report passed with `--input` usually is) carries each value in `Secret`, `Match` and `Line`. The stored copy now drops those fields, and `Author` and `Email`, from every entry before it is written and redacted, so a token in a format the redaction rules do not know (a GitLab token, a `credential = "..."` line) no longer lands in `raw/`.
- **Untriaged secrets hits can be triaged on a later audit.** The triage now offers every open, untriaged secrets hit of a system, not only the hits that audit found first (at most 20 per audit). `store.cjs findings` gains `--class`.
- **Switching dependency tools no longer counts a package twice.** A finished dependency scan closes the system's earlier findings from trivy, the npm audit and the pnpm audit that it no longer lists, whichever tool ran.
- **One checkout is one system.** The inventory folds the repo systems it detects in one folder into one system with every detected pack (a Next.js app with a `wrangler.toml` is one `web-nextjs` system with the `web-nextjs` and `cloudflare-workers` packs), so each checkout is scanned and triaged once.
- **No credentials in project addresses.** The store refuses a `live.url` with a user, password or token before the host, and a `host.ssh` written `user:pass@host`, naming the field and never the value.
- **Narrower git pre-approvals.** The skill pre-approves `git config user.name`, `git remote get-url` and `git rev-parse` instead of every git command. The `--repo` check reads the remote through `inventory-scan.cjs <folder> --remote`, which removes credentials from it.
- **The dashboard trend is right.** The score snapshot keeps the trend it was saved with, and the dashboard shows it, so a tile no longer reads "0.0, no change" right after every job.
- **Installable as its own marketplace.** `.claude-plugin/marketplace.json` lists the plugin, so `/plugin marketplace add FoodBreakPedro/rampart` and `/plugin install rampart@rampart` can work. `npm run validate` checks both manifests.
- A rotated history leak marked fixed stays fixed when gitleaks reports it again, since the history cannot un-leak.
- Finding text (title, evidence, exploit scenario, preconditions, recommendation) is redacted as it enters the store.
- A JWT right after a URL-encoded character (`Bearer%20…`, `token%3D…`) is redacted.
- On Windows, a file write retries a rename that an antivirus scanner or indexer briefly locks, and a torn last line in `scores.jsonl` no longer blocks scoring.
- The raw copy of a headers check keeps the requested URL without its query and fragment.
- Dashboard: the copy buttons are no longer marked disabled, the copy fallback can take focus, faint text and the light grade-D badge meet 4.5:1 contrast, long names wrap, and only layers with an engine (L1 for now) get a Run button.
- Node 20 or newer (Node 18 is past its end of life); `/rampart doctor` checks for 20.

### Known limitations

- No project grades above C: repo systems declare L2 and L3, which have no engine until Plan 2, so their coverage is capped even with zero findings.
- Real gitleaks and trivy runs were not exercised on the build machine; the secrets and dependency checks were tested with recorded reports and fake binaries.
- The secrets triage reads a leak's commit with git only when the repository is the session's working directory; otherwise it judges from the working tree.
- A dependency scan with a different tool than the last one closes the other tool's findings for that system, so a machine with only npm closes the pip or Go findings trivy reported until trivy runs again.

## 0.1.0-alpha.1 — 2026-10-23

- Plugin manifest and the `/rampart` front desk: one skill that routes a request to its job, a four-option menu when none is named, and shared rules every job follows (owner attestation gate, inventory-only targets, no credential values, read and report only).
- `/rampart inventory`: a deterministic scanner that detects Next.js, Node API, Expo, Supabase, n8n, Docker Compose, Cloudflare Workers and WordPress systems in a folder, an optional `inventory-mapper` agent run (sonnet) to refine the draft, and a confirmed `project.json` with your owner attestation.

- `/rampart audit L1` dependency check: trivy, or the npm or pnpm audit when trivy is missing, with one finding per vulnerable package; or a trivy or npm audit report passed with `--input`.
- `/rampart audit L1` headers check: one GET of each live URL, redirects followed, graded Observatory-style, with gaps recorded as hardening notes; an unreachable URL becomes a skipped run with its reason.
- Per-user store in `~/.rampart` (or `RAMPART_HOME`): projects, findings with stable ids that dedupe across runs, regressions that keep their first-seen date, findings closed when a scan no longer reports them, dispositions and runs, all as plain JSON and JSONL.
- Redaction of credential values in every tool report before it is written.
- JSON schemas for projects, findings, runs and jobs, with a zero-dependency validator.
- Score sheet (`score.cjs`): coverage out of 40 and findings out of 60 by finding class (`verified`, `tool`, `hardening`) and severity, letter grades, criticality weights and a trend against the last saved score.
- `/rampart doctor`: Node, gitleaks, trivy, python3, gh, ssh and git, the `claude-security` plugin, the store and packs, and what degrades without each.
- `/rampart dashboard --static`: every project as a tile with grade, score, open findings by severity and layer freshness, plus a per-project score sheet, as one HTML file in the store that works in light and dark and at phone width.
- Test suite on the built-in `node:test` runner, with no npm dependencies.
